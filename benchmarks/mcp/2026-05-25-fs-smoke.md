**Status**: ✓ pass. Single-prompt smoke, not a perf claim. See

  Connected in 1951 ms, protocol version `2025-06-18` negotiated.

## Findings worth recording (non-perf)

- **CORS path**: WebUI hits the MCP server **directly** from the
  browser, not via llama-server's `/cors-proxy`. The proxy flag matters
  for *other* WebUI features (favicons etc.) but MCP requires CORS on
  the bridge itself.
- **Transport**: WebUI only speaks **Streamable HTTP** (`POST /mcp`).
  supergateway's default `stdioToSse` mode (`/sse` + `/message`) fails
  with "Cannot POST /sse". Must use `--outputTransport streamableHttp`.
- **localStorage key**: `LlamaCppWebui.mcpDefaultEnabled` holds the
  server list. Per-browser; clear it to reset.
- **Outbound leak under `MCP_PROXY=1`**: WebUI also proxies favicon
  fetches via `/cors-proxy?url=…google.com…`. Real outbound traffic.
  Confirmed in turboquant.log:
  `proxy_request: proxying GET request to https://www.google.com:443/s2/favicons`.
  Justifies the off-by-default policy in `docs/mcp-integration.md`.

## Prompt and result

Prompt: `List the files in the repository root directory. Use the filesystem tool.`

1. Tool call: `list_allowed_directories` → returned sandbox root
2. Tool call: `list_directory(path=...)` → returned 30 entries
3. Final NL summary listing all 30 files and dirs correctly (including
   files created earlier in the same session: `.venv/`,
   `requirements-tui.txt`, `.playwright-mcp/`, `TODO.md`).

## What this proves / does not prove

✓ Wiring works end-to-end: env var → start script → llama-server flag →
  WebUI talks to MCP server via bridge → model emits tool calls →
  results flow back → model uses them in the final answer.

✗ Does **not** prove throughput, latency, robustness under multi-turn,
  tool-call accuracy under load, or behavior on other models. Single
  prompt, single model, single session.
